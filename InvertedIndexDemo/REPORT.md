# Звіт: інвертований індекс

## Опис реалізації

Клас Document зберігає Id, Title і Content. Клас TextProcessor має метод Tokenize, який переводить текст у нижній регістр і розбиває його на слова через Regex з шаблоном \w+ (так прибирається пунктуація). Метод NormalizeWord застосовує те саме правило до слова запиту, наприклад c# перетворюється на c. Завдяки цьому індекс і лінійний пошук нормалізують текст однаково.

Клас InvertedIndex зберігає два словники: Dictionary<string, HashSet<int>> (слово і множина id документів) та Dictionary<int, Document> (id і документ). Метод SearchSingleWord нормалізує слово запиту й бере множину id зі словника через допоміжний метод GetIds (якщо слова в індексі немає, повертається порожня множина). Метод SearchMultipleWords (AND) послідовно викликає IntersectWith для множин слів, а SearchAnyWord (OR) викликає UnionWith.

Клас PerformanceTest окремо вимірює побудову індексу, лінійний пошук (при кожному запиті токенізуються тексти всіх документів) і пошук через індекс. Перед вимірами виконано розігрівальний запуск на п'яти документах, а кількість знайдених документів у двох підходів порівнюється.

## Висновок

Лінійний пошук перебирає всі документи й щоразу розбиває текст на слова, тому його час росте разом із кількістю документів: від 636 тіків для 10 документів до 269062 для 10000. Пошук через індекс це одне звернення до словника за ключем, тому він швидкий на будь-якому обсязі: 134 тіки для 10 документів і 4555 для 10000. На 10000 документів індекс швидший приблизно в 59 разів.

Побудова індексу коштує дорожче за один лінійний пошук (на 10000 документів 441824 тіки проти 269062). Тому для одного запиту індекс не вигідний: побудова разом із пошуком займає більше часу, ніж просто лінійний пошук.

Поріг вигідності залежить від кількості запитів. Індекс окупається, коли побудова розподіляється на кілька пошуків. Для 10 документів різниця між лінійним пошуком і пошуком через індекс становить 502 тіки, а побудова коштує 832, тож індекс окупається приблизно з другого запиту. Для 1000 документів це 49356 проти 53985, тобто теж приблизно з другого запиту. Для 10000 документів це 264507 проти 441824, тож знову приблизно з другого запиту. Отже, якщо за одними й тими самими документами шукають двічі й більше, індекс вигідніший, а якщо шукають один раз, достатньо лінійного пошуку.

Результат на 100 документах (3583 тіки для індексу) виглядає завищеним порівняно з 1000 документами (544 тіки). Імовірно, виміри дуже короткі, тому на них впливають JIT-компіляція і кеш процесора. Загальна тенденція від цього не змінюється.

В усіх тестах обидва способи знайшли однакову кількість документів, тому порівняння коректне: нормалізація тексту для обох однакова (нижній регістр і розбиття через `\w+`).

## Контрольні питання

1. Чому структура Dictionary<string, HashSet<int>> добре підходить для реалізації інвертованого індексу?
Ключем є слово, а значенням множина id документів. Словник швидко знаходить слово, а HashSet не дублює id, якщо слово повторюється в документі, і має готові операції над множинами.

2. Які переваги HashSet<T> дає під час обчислення AND/OR-пошуку за кількома словами?
IntersectWith залишає документи, спільні для всіх слів (AND), а UnionWith об'єднує множини (OR). Операції швидкі, а дублікатів у результаті немає.

3. Чому під час вимірювання продуктивності важливо однаково нормалізувати текст для лінійного пошуку та пошуку через індекс?
Якщо нормалізація різна (регістр, пунктуація), два підходи можуть знаходити різні документи і виконувати різний обсяг роботи, тому порівняння часу буде некоректним. Тому використовується один Tokenize, а кількість знайдених документів перевіряється.

4. Які обмеження має проста реалізація інвертованого індексу без ранжування, стемінгу та підтримки фраз?
Результати не впорядковані за релевантністю, різні форми слова (language і languages) вважаються різними словами, не можна шукати точну фразу. Також індекс займає пам'ять і його потрібно оновлювати при зміні документів.
